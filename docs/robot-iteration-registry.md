# 机器人迭代记录与复盘体系（2026-08-21 建立）

> 解决的问题：历史版本难定位、记录与代码版本对不上（脏树运行 / 指纹不含 commit）、
> 分数口径漂移（历史记录只显示 base 分）、同一实验被重复跑浪费时间。
> 核心原则：**版本登记（`versions.json`）是唯一真相源，页面与报告全部从数据生成，
> 绝不重跑同一版本，每个历史版本都有完整复盘记录。**
> 配套入口：`node tools/robot_iterate.js`（标准迭代入口，见 §2）。

现行迭代 loop 的统一规范位于 **§2.1**：目标分层、小目标 PASS、验收门限、
预算截断专项循环与留档要求集中维护于此。调研工具说明及阶段计划引用本节，
不另设一套通用门槛；历史版本成绩和阶段门限仅用于追溯。

## 1. 数据流与文件

```text
人工维护（真相源）                   自动生成
reports/iteration/versions.json ─┐
reports/research/*.json（调研记录）├─→ tools/robot-iteration-lib.js
seti-saves/*.json（存档，可选）    │      └→ reports/iteration/registry.json（构建产物）
                                 │      └→ reports/robot-iteration.html（总览页，数据内嵌）
                                 └──→ reports/iteration/<version-id>/<record-key>.action-log.html
                                          （逐步复盘报告，纯重放存档 replaySteps）
```

| 文件 | 角色 |
|---|---|
| `reports/iteration/versions.json` | **唯一真相源**（人工维护）：版本定义、改动摘要、记录归属、roadmap 注记 |
| `reports/research/*.json` | 调研记录（`run_research_validation.js` 产物，指纹含 gitCommit） |
| `seti-saves/*.json` | 存档（可选）；有存档的终局运行可读完整终局分、可生成复盘报告 |
| `reports/iteration/registry.json` | 构建产物：版本+结果+best-of+审计合并后的数据 |
| `reports/robot-iteration.html` | 总览页：顶部最佳卡 + 当前 baseline 迭表（**历史版本折叠归档**）；数据内嵌可离线打开 |
| `reports/iteration/<vid>/<key>.action-log.html` | 逐步复盘报告 |
| `tools/robot_iterate.js` | 标准迭代入口 CLI |
| `tools/robot-iteration-lib.js` | 核心库（扫描/富化/best-of/审计/报告/渲染） |

## 2. 标准迭代入口

搜索触限记录（2026-09-11）：每次真实搜索的 `metrics.searches[].diagnostics.budgetLimits`
保留 leaves/frontier/execution 三类实际上限及 enabled/reached/truncated 状态；调研终端
逐次输出启用且触顶或截断的限制，不只保留 Top 20。action-log 报告读取关联调研记录，
列出全部搜索明细；决策搜索报告也展示三类状态。战略 8 叶限制未启用，不能记为未触发。
旧记录缺字段显示“未记录”，不补造零次、不重跑已有实验；计划复用不重复记数。
已有 `budgetHits` 仍专指执行预算耗尽且剩余队列非空，不能用于代替三类触限统计。
完整局验证保留用户可见的实时原始进度与触限输出（2026-09-11 用户确认），包含轮次、
回合、决策数、席位、动作、各席分数和耗时；写日志时也须持续向终端展示增量进度，
不只在结束后给汇总。运行中的分数不得冒充正式终局成绩。
对话工具转发进度时直接输出stdout文本，不将整份进程结果序列化为含转义换行的JSON；
后台采集以约10秒的短间隔读取同一存活进程，不用40秒批量输出及口头摘要替代原始进度
（2026-09-12用户再次指出显示中断）。无新输出不等于进程结束，不因此重启实验。
已有报告需用 `node tools/robot_iterate.js build --reports --force-reports` 重建展示；只读记录并重放
存档，不重跑 AI，也不能补回运行时没有记录的字段。

### 2.1 迭代 loop 统一规范（2026-09-11 用户确认）

#### 大目标、小目标与 PASS

**目标分层（2026-09-11 用户确认）：迭代分为大目标和小目标。**

- 大目标：一个专项目标，例如“消除全部预算截断”；定义专项范围和最终完成条件，
  由一组小目标组成推进计划。
- 小目标：服务于某个大目标的具体迭代项，有自己的目标和 PASS 条件；记录所属大目标
  及本项贡献，按自身目标验收。
- 小目标来源（2026-09-11 用户确认）：一是策略审阅中已登记的
  [TODO](../reports/iteration/strategy-todo-20260911.md)，二是根据大目标分析、拆解得到的
  中间小目标。两类都纳入同一迭代流程，执行前明确所属大目标和自身 PASS 条件；
  保留 TODO 已确认的优先级与范围，“仅观测”项不自动升级为修复任务。
- 小目标通过不等于大目标完成；大目标须按自己的最终条件验收，不能仅凭已完成若干
  小目标推断通过。上述预算截断目标在此用于说明层级，不代表本次已启动该专项。

**小迭代 PASS 标准（2026-09-11 用户确认）：每项小迭代有自己的目标；目标经证据
验证达成，且该项是整体计划的一部分，即可按小迭代通过。** 不把整体计划的最终目标
逐项套到每个小迭代上，不要求每项都涨分或消除全部搜索截断。整体计划是否完成另行验收。
本文其他阶段记录中的固定分数门槛不自动成为当前每项小迭代的通过门槛。

**长期效果方向（2026-09-11 用户确认）：随着搜索越来越完备，长期迭代期望整体
得分上涨。** 不要求每项涨分，是将单项验收与长期效果分开，不是放弃得分提升。
阶段复盘须在可比的规则、盘面和配置下，结合完整终局成绩观察搜索完备性与得分趋势；
若搜索更完备但得分持续不升或下降，应分析估值、候选选择与计划执行等原因，并据证据
形成后续小目标，不能长期只以局部目标达成为由忽略整体效果。该期望不等于每步单调
上涨，也不要求恢复已纠正的错误收益；具体涨幅、统计窗口和退化底线尚未定值。

每项开工前记录：本项目标、所属整体计划及贡献、可判定的 PASS 条件、验证证据与
影响边界。收口时逐项对照目标，记录结果和整体计划剩余事项；不能事后改目标来制造通过。
策略必要性先于实现优化（2026-09-11 用户确认）：逐项说明策略解决的真实决策问题、
去掉后会出现的具体错误，以及正式收益计算或已有搜索为何尚未覆盖该问题。
不能仅因已有策略存在就保留，也不能用调准权重或实验涨分替代必要性证明。
没有必要的策略应删除；确有未覆盖收益时，先核对受益人、触发条件与重复计入边界，
再决定是否需要独立策略补偿。
本次对齐的是通过判据，不取消正确性、异常暴露、实验去重和留档要求；验证执行频率
（如完整局每项执行还是阶段执行）尚未重新对齐，不因本条自动豁免既有验证要求。

1. 先有想法与计划：改动前写清目的、预期行为、预期分数变化、影响边界和可证伪证据；实现后逐项复核，不靠得分上涨
   推断逻辑正确。检查受影响消费者、正式规则/状态/资源和恢复边界，避免引入新bug。
2. 开发完成先确认实现符合计划，再以测试和实验验证本项 PASS 条件。分数变化是
   观测证据；除非本项目标包含分数要求，不因分数单项升降直接判通过、失败或回滚。
   非预期变化仍需记录并归因，不直接调权重补分：
   - **其他代码问题牵连**：先以证据说明具体问题及关联，分别记录本项目标是否达成
     与外部问题；明确 bug 按下述插入式修复流程处理，独立计划、验证、提交和登记，不混入原策略
     摘要。未证明由本轮引入的缺陷，不称为本轮导致的次生问题。
   - **策略本身未达到本项目标**：记录未通过及原因，重设计或回滚本项；不能因为
     代码已实现就宣称目标达成。回滚不连带撤销独立正确规则修复。
   - **原因未明**：明确未知项；若本项目标因此无法验证，不宣称通过；与本项无关的
     未决问题留给对应计划项，不把所有整体问题都变成本项门槛。
3. 策略与性能改动按本项目标验收：分数、搜索覆盖、节点成本、可解释性等是否作为
   PASS 条件应事先明确，不统一要求均分提高或不下降。涉及终局成绩的验证仍须使用
   完整终局，快速阶段分数不能替代。未达标如实记录，不为追回分数恢复已确认错误的逻辑。
   **规则bug例外（2026-09-07用户明确）**：已确认的规则bug修复以符合正式规则、实现
   正确为验收依据，不要求维持含错误收益的历史分数。仍跑完整局检查执行异常、连带
   问题并记录新分数；正常的纠错降分不阻塞该规则修复通过，也不触发回滚。此例外不
   扩展为策略或性能改动免除效果验收，不把所有下降自动归为规则纠错。
4. 均分提升也不自动收口：核对实现、相关行为回归与新bug风险，明确证据覆盖不到的
   边界。测试通过不是无bug保证；不得绕过错误或用无意义构造测试制造“全绿”。用户明确
   暂不处理的既有失败需列明，不伪称全量通过，也不擅自扩大本轮修复范围。
5. 每轮完成后登记版本、同步文档并向用户报告：改了什么、预期与实际、验证证据、完整
   终局、已知问题与未完成项。摘要只写改动；成绩与验收结论放结果注记。遵守固定实验
   去重，保留失败候选及独立修复记录，不混淆版本贡献。
6. 范围审查（2026-09-06）：持续判断工作是否直接服务于本轮目的；用户提醒不等于
   已证明方向错误，应自行依据证据判断。完整设计覆盖本次问题的执行边界，不自动
   扩成所有同类机制的重构。跨模块审查可必要，但新增基础设施需证明必要性；未证明
   关联的缺陷单独记录，不以减少文件数或提高均分替代正确性，也不无限阻塞主线。

本标准是后续迭代的固定流程，不因某轮得分提高而省略；详见当轮计划与验收矩阵。

#### 明确 bug 的插入式修复（2026-09-11 用户确认）

迭代中发现明确 bug，插入修复小目标优先处理，不要求它恰好属于当前最大搜索热点。

1. 确认：记录实际行为、应有行为、输入与代码证据；有可复现案例时先复现。尚未确认
   的疑点先取证，不凭猜测修改，也不把策略取舍直接归类为 bug。
2. 插入：保留当前大目标、小目标的进度、已有证据及恢复点；登记独立 bug 修复项，
   写清修复目标、影响范围和 PASS 条件，不将修复效果混算为原优化的贡献。
3. 修复：完成有依据的修复与针对性回归，按既定门限验证、同步文档并独立提交留档；
   不吞错、不用绕过性补丁，也不借机扩大为无关重构。
4. 恢复：修复通过后回到原小目标／专项 loop。若修复改变规则或搜索状态，重新核对
   原证据与热点排序的适用性；关联修复前后版本，不沿用已经失效的验收证据。

修复完成不代表原小目标或大目标完成。用户已明确暂缓、仅观测或排除的范围仍有效，
需要改变该范围时先对齐；未确认问题不自动触发实现。

#### 验收门限与运行限制

| 项目 | 现行要求 | 适用层级 |
|---|---|---|
| 运行正确性 | 实际规则执行失败、异常和必需字段缺失归零；禁止吞错、过滤失败或补默认值制造通过。正常可选空值须有契约解释 | 验证与运行的共同要求 |
| 回归验证 | 相关 unit 与唯一 full-flow 验证；测试分类按 [Node 测试标准](node-testing.md)。既有失败单列并核实，不宣称全绿 | 按修改范围验证 |
| 完整局 | 固定盘面自然完成终局，保留正式终局分及拆分；快速验证不替代终局 | 完整局证据要求；小目标／阶段执行频率尚待对齐，既有要求不自动豁免 |
| 战略运行预算 | 最多 4096 执行节点、256 个保留队列节点、30000ms 搜索期限；战略 maxLeaves=8 参数不启用叶数截断，control 使用自己的实际配置 | 运行限制，不是每个小目标统一 PASS 门限 |
| 预算截断 | “全部预算截断归零”按专项范围验收；达到上限但自然完成不算截断。分别报告各限制的启用、触顶及截断，缺失记录不能算零次 | 大目标；小目标按自己的改善目标验收 |
| 分数、节点与耗时改善 | 无统一涨分要求、固定分数线或改善百分比；本项目标涉及哪项指标，开工前定义对应门限并提供证据 | 小目标分别定义 |
| 长期得分趋势 | 期望随搜索完备性提升而整体上涨；阶段复盘检查可比完整局趋势，持续不升或下降须分析并形成后续改进，不以单项 PASS 代替整体效果 | 长期／阶段方向，不是每项单调涨分门槛 |
| 记录完整性 | 关联大目标、小目标、代码提交、配置、输入／checkpoint、日志、存档、报告和 PASS／未通过原因；实验去重，失败结果也留档 | 每项迭代 |

30 秒是搜索内部期限，不是完整机器人决策总耗时承诺；宏步不能中途抢占，超时须
显式报告，不以耗时统计代替异常检查。预算实现契约见 [AI 设计](ai-design.md)。
历史“单决策 10 秒”和阶段固定分数门槛不直接作为本轮通用门限。

尚未统一的两项：每个小目标／阶段的完整局验证频率；非本项目标指标的退化底线。
在后续对齐前不臆造数值，也不把“未设统一门限”解释为可以隐瞒退化或豁免验证。

#### 每项小目标的查询与交接记录

- 开工：小目标 ID／名称、所属大目标、来源 TODO 或瓶颈证据、目标及贡献、PASS 条件、影响边界。
- 结果：实现提交、验证命令与配置、证据路径、指标前后变化、既有／新增异常和未决事项。
- 收口：本项目标逐项达成情况、PASS／未通过结论、大目标剩余工作和下一瓶颈；大目标完成另附验收证据。

#### 临时目录迭代、合回与报告中心（2026-09-11 用户确认）

1. 每次实际迭代新建独立临时目录，记录目录路径、起始提交、目标 ID 和实验配置。
   在该目录完成设计、代码／文档修改与验证，不在共享主目录试改策略；插入式 bug
   修复同样隔离，并保存原小目标恢复点。主目录保持 dev，不为隔离切换共享分支。
2. 起点使用明确的已提交版本；不得隐式带入主目录其他人的未提交改动。实验记录
   必须对应临时目录的实际代码提交，遵循全项目已有记录去重，不能因换目录重复实验。
3. 小目标验收后，将通过的代码、同步文档和验证产物合回主目录；核对期间主目录
   新增改动与冲突，只合入本项内容，不整目录覆盖。保留受测提交及其追溯关系；合回
   导致代码内容变化时补相应验证，不把临时目录证据冒充合并后不同代码的验收证据。
4. 更新仓库机器人报告中心：合并版本登记 `reports/iteration/versions.json`、研究记录、
   存档及本项报告，以标准 build 更新 `reports/iteration/registry.json`、
   `reports/robot-iteration.html` 和逐步复盘报告。核对版本／提交、成绩与触限口径、
   PASS／未通过结论及链接，不通过重跑同版本实验补展示。
5. 未通过时保留失败记录与原因并更新报告中心，不把未通过策略合成已接受版本。
   结果合回和报告中心核验完成前，不能仅以临时目录测试通过宣称交付完成；临时目录
   在证据可靠归档前保留，清理不得影响主目录或其他迭代。

当前报告中心指本仓库机器人版本总览与复盘页，不自动包含外部发布。
本轮执行顺序见 [策略 TODO 的已确认迭代顺序](../reports/iteration/strategy-todo-20260911.md)：
ALIEN-VALUE-01 → TURN-BOUNDARY-01 → QUICK-TIMING-01 → GOAL-ONLY-01 →
预算截断专项循环直至达成 → DATA-PLACEMENT-01 → ROUND-PLAN-01。

#### “消除全部预算截断”专项的自迭代流程（2026-09-11 用户确认）

1. 定位当前瓶颈：从当前版本记录中筛选实际发生预算截断的决策，优先选择执行节点数
   最大的一项。这里的“节点”定位到一次决策的搜索，不把正常触顶但已完成的搜索算成截断。
   多项都达到同一节点上限时，记录并列情况，不能臆测未执行部分的总节点数。
2. 拆解节点分布：查看该决策内部各动作、条件选择及目标路线的节点量，找到最大的
   搜索部分，并定位对应输入和实现；物理节点数与多目标来源计数分开，不混算占比。
3. 形成小目标：针对最大头，分析如何用贪心选择替代展开，或消除不必要搜索。
   写清选择依据、预期减少的搜索及本项 PASS 条件。贪心属于策略取舍，说明可能
   放弃的方案；无损剪枝须有等价或不可达依据，两者不混称为无损优化。
4. 实现并验证：按小目标完成设计、修改、验证与版本留档，记录前后节点分布、截断
   和行为变化。小目标达到自身条件即可通过，不要求一次消除专项的全部截断。
5. 更新瓶颈并继续：用迭代后的记录重新找当前触发截断且节点量最大的决策，重新分析
   最大头、生成下一小目标、实现验证；如此往复，直到专项目标经证据验收达成。
   不因一个小目标通过或原瓶颈消失就结束专项，也不一直沿用已经变化的热点排序。

过程记录须可串联：所属大目标 → 本次选中的决策及记录来源 → 最大头分析 → 小目标
及 PASS 证据 → 更新后的瓶颈／专项完成证据。预算阈值保持既定口径，不靠扩大预算、
隐藏截断或把有损搜索标成完整来达成目标；实验去重及验证要求继续适用。
当前是在登记专项方法，不表示已启动实验或已达到专项目标。

阶段目标与历史进度按需查阅 [阶段进度](progress-20260912.md)。

### 2.2 执行与登记

每次迭代只做两件事：**改核心策略 + 分析历史版本**。迭代闭环：

```text
1. 按 §2.1 新建独立临时目录，在其中改核心策略、同步文档（改动即文档）并提交代码
2. node tools/robot_iterate.js run --name <id> [--full] [--steps N] [--config k=v] --summary "..."
   → 跑验证（底层指纹去重，绝不重跑）
   → 自动登记版本（head/commits/baseline 自动推导，写 versions.json 前自动 .bak 备份）
   → 生成复盘报告（纯重放，无 AI 重跑）→ 重建总览页

`run` 的子进程用**异步 spawn 实时透传** stdout/stderr（2026-08-21 修复，替代原 spawnSync
同步阻塞）：全盘数分钟期间，run_research_validation 默认逐决策写 stderr 的进度行
（`progress.js`，minIntervalMs=1000：轮次/回合/决策#/席位/动作/各席分数/用时）会实时
出现在终端，而不是等结束才一次性吐出；`--progress N` 的每 N 步汇总同样实时可见。
3. 人工核对 versions.json 的 summary / 记录注记（可再跑 register/build 微调）
4. 提交记录体系产物；按 §2.1 验收后合回主目录，并更新核验主目录报告中心
5. 分析历史：review --best / --show / --compare / check
```

命令一览：

```sh
# 跑验证 + 登记 + 报告 + 页面（默认 200 步快速；--full 全盘）
node tools/robot_iterate.js run --name card-value-fix --full --summary "打牌价值修正：…"
node tools/robot_iterate.js run --name search-timing --steps 200 --config planNewTurnReuse=false

# 手动登记已有记录为版本（不重跑；幂等，已有定义保持不变）
node tools/robot_iterate.js register --version-id <id> --name "显示名" --summary "…" \
    --commits abc1234,def5678 --records fp.commit.full.json --baseline <vid> --date YYYY-MM-DD

# 重建 registry + 页面；--reports 为所有有存档但缺报告的记录补齐复盘报告
node tools/robot_iterate.js build [--reports]

# 历史分析（只读）
node tools/robot_iterate.js review --best                 # 固定盘面最佳（白分/均分/耗时）
node tools/robot_iterate.js review --show <id>            # 版本详情（提交/结果/回退命令）
node tools/robot_iterate.js review --compare <a>..<b>     # 两版本对比
node tools/robot_iterate.js check                         # 完整性审计（exit 1 = 有警告）
```

`run` 的防重跑双层保障：

1. **登记守卫**：同一版本 id 已登记于当前 HEAD → 直接拒绝（exit 2）。
2. **底层指纹去重**：`run_research_validation` 指纹含 gitCommit，同实验同代码版本同模式已有
   记录 → exit 2；`--force` 覆盖前自动备份旧记录。

**绝不重跑**：同一代码版本（head）绝不跑两遍。行为改动 → 新 commit → 自动新指纹新记录。

## 3. versions.json 版本登记 schema

```jsonc
{
  "schemaVersion": "seti-robot-iteration-registry-v1",
  "defaultBoard": { "seed": "seti-free-analyze-v1", "name": "免电分析盘面", "note": "…" },
  "versions": [                    // 数组顺序 = 最新在前（页面倒序展示）
    {
      "id": "v0",                 // 稳定 id（页面/回退/对比都用它）
      "name": "v0 基线（当前代码默认装配）",
      "date": "2026-08-18",
      "baseline": null,            // 基线版本 id（该版本基于哪个版本）
      "head": "53abbd5a",          // 该版本代码树（记录 gitCommit 的对照基准）
      "commits": ["6caeb0f7", "10ded3e9", "dd5da46e", "53abbd5a"],  // 本版本引入的提交（旧→新）
      "summary": "改动摘要（人工撰写）",
      "records": {                 // 记录归属：reports/research/ 下的文件名 → 注记
        "d2c50ffe.53abbd5.full.json": { "note": "on-head：557 步，完整终局 107/68/98/83 均 89" }
      },
      "roadmap": null              // 无 research 记录时的手工分数（来源标注 roadmap）
    }
  ]
}
```

改动摘要 `summary` 只描述改了什么；分数、步数、验证结果和验收结论放在实验结果或记录注记中，不混入改动摘要。

归属规则：

- **每个固定盘面的全盘记录必须归属到某个版本**（`check` 会把未归属的全盘记录列为
  **warn 级孤儿记录**）——孤儿记录说明有实验跑了但没登记，页面会一直提示直到登记。
- 记录 gitCommit 应在版本 commits 内（前缀匹配）。运行于**脏工作树**时记录 gitCommit
  取 HEAD、可能与实际代码不符——这种情况下在记录注记里写明，并接受 audit 的
  provenance 警告。
- 进行中的实验（未收口、脏树运行）**不登记为版本**，以孤儿记录形式留在页面上
  可见，收口后再 register。

## 4. 分数口径（用户规定：所有分数以最终总分为准）

每份结果的 `scoreSource` 三档优先级：

| 来源 | 说明 |
|---|---|
| `save-final` | 有存档的终局运行：从存档 `committedState.match.finalScores` 读**完整终局分**（total = base + 板块 + 卡牌），最可信 |
| `record` | 无存档/非终局：用记录 `summary.scores`（当时运行口径；2026-08-20 finalScore 修复前只显示 base 分） |
| `roadmap` | 无 research 记录：用 versions.json 的 `roadmap` 字段（文档来源记录的分） |

页面每个分数格都带来源徽标，杜绝口径混用（旧总览页的教训：base 分与完整分混在一张表里）。

## 5. 逐步复盘报告（每个实验的完整复盘记录）

**硬规矩（2026-08-21 用户口径）**：标准迭代入口 `robot_iterate run` **默认**产出完整复盘三件套
（存档 + 复盘报告 + 记录）：跑验证默认写存档（不经 `--no-save`）→ 自动登记版本 → 从存档
纯重放生成行动级复盘报告 → run 结束**硬校验**：记录/存档/复盘报告任一缺失即显式失败
（exit 非 0，提示原因），不允许"跑完没复盘"的迭代收口。`build --reports` 可补齐缺报告记录。

生成方式：`node tools/robot_iterate.js build --reports`（为所有有存档但缺报告的记录补齐；
报告模板/聚合逻辑改动后用 `--force-reports` 强制重新生成全部报告）。**纯重放存档
`replaySteps`（`after` 快照含每步后的分数/钱/电/宣传/手牌），不做任何 AI 搜索——绝不重跑。**

报告内容（2026-08-21 起按**玩家回合**聚合——2026-08-21 用户口径：一个玩家的回合 =
主行动 + 附属快速/条件步骤合并为一行，不再把打牌/选目标等子步骤拆行）：

- 头部：seed / gitCommit / policy / flags / 模式 / 步数 / 耗时 + 记录 JSON 与存档路径
- 终局分数表：完整终局分 + base/板块/卡牌拆分 + 均分；**结算明细**——每玩家列出
  base 构成（初始/扫描/环绕/登陆/蓝科技/科技bonus/外星痕迹/卡牌效果等，逐项分数）、
  各板块得分、卡牌得分（卡名+分数），即"具体什么获得了几分"（2026-08-21 用户口径）
- **每名玩家行动清单**：按蓝/绿/棕/白分组，每玩家**每回合一行**（轮/回合、主行动
  标签+摘要、该回合步数、分数变化、回合后分数与资源）；初始选择并入该玩家第一回合；
  **纯 end_turn（结束回合）回合不展示**——结束回合不是玩家一动（2026-08-21 用户口径）；
  **卡牌编号显示为卡牌名称**（`assets/cards/card_model.json` + `assets/aliens/*/card_model.csv`
  GBK 解码，外星卡 id 拼接物种前缀；查不到的保留原编号）；
  **该回合的附属动作按发生顺序合并为一行列出**（快速/盲抽/收入/终局标记/初始牌，
  2026-08-21 用户口径）：快速行动摘要完整；**盲抽/精选显示抽到的牌**（重放对比 hand 增量，
  如"抽牌 大耳朵射电望远镜"）；**收入显示插的牌与获得资源**（重放对比 income 增量，
  如"收入 水手10号任务（获得 信用点+1）"，按插牌 income 码给单一资源——orbit 摘要中
  误导性的"获得 1 次收入（R1，1信用点+1能量）"文案已修正为"获得 1 次收入"）；终局标记、
  初始牌（编号+效果）同样并入。条件/目标选择子步骤仍并入回合不单列；纯 end_turn 回合不展示。
- **全程依次复盘**：按轮分组的全量玩家回合时间线（同上一行格式，含玩家列；同样不展示纯 end_turn 回合）
- 行动族统计（记录级，全量步骤口径）

没有存档的记录无法生成行动级报告——页面标注"仅记录级指标"（记录 JSON 本身含
行动族分布/外星时间线，仍可复盘）。`check` 会列出有存档但缺报告的记录。

## 7. 完整性审计（命令行 check）

| 级别 | 检查项 |
|---|---|
| warn | 固定盘面全盘记录未归属任何版本（孤儿） |
| warn | 记录 gitCommit 不在版本 commits 内（provenance 不匹配，脏树运行需注记说明） |
| warn | 版本声明了不存在的记录文件 / 有存档但缺复盘报告 |
| info | 非全盘孤儿记录 / roadmap-only 版本 / 声明存档已删除 / 工作树脏 |

`check` 退出码 1 = 有 warn，用于 CI/提交前自查。
