## 五、实验计划（等负载降到个位数再跑）

**目标**：找出哪一档限制是"**分数中性**"的——即能显著减少节点/打满，而**均分守住 113.5**。

单旋钮配置（可直接粘贴为 `quotaTiers`，只保留一个字段）：

```
chain-only:    [{at:2048,chain:12},{at:3072,chain:10},{at:3584,chain:8},{at:3840,chain:6}]
entries-only:  [{at:2048,entries:16},{at:3072,entries:4},{at:3584,entries:1},{at:3840,entries:1}]
perTarget-only:[{at:2048,perTarget:4},{at:3072,perTarget:2},{at:3584,perTarget:1},{at:3840,perTarget:1}]
```

执行方式（沿用已验证的流程）：
1. 在隔离临时目录分别提交三个"单旋钮"版本（把配置写成代码默认，**不靠 env**——env 不进版本指纹，
   会导致 `robot_iterate` 判为同一版本而拒绝重跑，这个坑已经踩过）；
2. 每个版本跑一局完整局（`--full`），记录：均分与逐席分账、节点均值、打满次数、最慢决策、整局耗时；
3. **门禁**：均分 ≥113.5。达标者保留并复测；掉分者按失败留档（附分数/节点/打满三项数据）。
4. 计时纪律：所有耗时数字必须等 loadavg 个位数，且同一负载下交替测（同一份未改动代码在 482 上
   实测过 20.4 / 25.2 / 28.8 / 34.3s）。
5. 若三档单独都掉分 → 判定"减节点与守分在本世界冲突"，按目标要求留曲线判未达成，
   不得用掉分换时间。

## 十一、owner 指定的判定流程（剪枝后动作发生变化时）

当剪枝导致**动作**变化时，按以下两步自查，而不是直接判失败：

1. **原有选择是否被剪枝掉？**
   - 若被剪枝：**是否符合预期**——即它是否本就属于该被砍的那类分支（深宏步链/低价值延续）；
   - 检查手段：该决策诊断里的 `macroChainCapPrunedCount` / `searchCompleteness.reasons`（是否含 chain 相关原因）、
     以及单决策对照（同输入分别跑 baseline 与剪枝配置，看 baseline 动作在剪枝配置下是否被裁掉/未入队）。
2. **新选择是否"新进入队列"的选项？**
   - 若是（即它在 baseline 里本来就在候选/前沿里、只是预算耗尽没轮到）：**只看最终分数是否增长**即可；
   - 检查手段：baseline 单决策的 `frontierNodeBreakdown` / 候选根动作集合里是否已含该动作。

**只有两种情况都解释不通时，才判为"剪枝误伤"**（即砍掉了本该被选中的高价值路径）。

配套工具：`adhoc/diff-runs-by-state.js`（比两个存档的逐 step 动作与 after 状态，打印首个及后续分叉点）。

## 十三、Round 50：**深度不是价值判据**——两版 chain 上限的对照把这条路证否了

| 配置 | 482 动作/计划 | 节点 | 截断 | 剩余队列 | chain 裁剪 | 完整局均分 |
|---|---|---|---|---|---|---|
| 基线（无上限） | industry:e887dc52 / 13 步 | 4096 | true | 244 | 0 | **113.5** |
| **chain-only（一刀切深度）** | 同 | 3424 | **false** | **0** | 660 | **102.25（−11.25）** |
| **chain v2（只限 move/quick_trade/card_corner 深链）** | 同 | 4096 | true | **225** | 419 | 未跑（收益已不足） |

**结论**：
- 一刀切深度上限的"省节点"效果，**主要来自砍掉 probe/launch/scan/place_data 这些非手段类深链**——
  也就是**真正承载分数的那些计划**（完整局步 44 蓝席发射计划被砍即为此）；
- 一旦把上限限制到手段类（v2），剩余队列只从 244 降到 225（−8%）、截断依旧——**几乎没有收益**。

**因此"按深度砍"这条路被双向证否**：能省则必掉分，想守分则省不到。
这与 owner 的判断完全一致：**深度本身不是价值判据**，应该由**未来价值估值**去识别"这条深链最终能不能兑现分数"，
再由贪心排序/剪枝自然淘汰无价值的部分——而不是用深度这个粗糙代理量。

### 下一步（唯一剩下的方向：修未来估值）

1. 先定义"节点未来价值"应折入什么：该路径剩余可达的**分数兑现**（目标完成后的得分、科技/终局牌/痕迹的兑现概率与数量、
   剩余收入发放），并保证**与叶值同尺度**（`primaryValue`：分差 + 基建差 + 宣传研究差）；
2. 用现成的**祖先口径差距指标**（`leafValue − min(祖先 nodeValue)`，482 实测最大 19.5 / 步37 实测 71.5）做验收：
   **修完后该差距分布应显著收紧**（越紧说明节点值越能预测后代值）；
3. 差距收紧后再回到 B（上界剪枝）与 C'（贪心排序），两者共用同一份估值改进。

## 十四、Round 51：**病根定位——节点优先级普遍为 0（没有未来项）**

数据：步 37 的 680 个叶配对（含祖先口径，已落盘 `budget37-leafvalue-20260913.json`）。

| 统计 | min | p50 | max |
|---|---|---|---|
| leafValue（叶的 primaryValue） | 0 | **46.0** | 71.5 |
| nodeValue（产出叶的节点 sortKey[2]） | 0 | 30.5 | 54.5 |
| **minAncestorNodeValue（路径上最小祖先节点值）** | 0 | **0.0** | **0.0** |

**祖先节点值分布：680/680 全部 ≤ 0。**

### 这意味着什么

`primaryValue = 分差 + 基建差 + 宣传研究差` 是**相对根的"已兑现"增量**：
蓝席在步 37 那个根动作上还没拿到任何分/基建时，节点值就是 **0**。而**从这些 0 值节点可以走到价值 46~71.5 的叶**。

因此：

1. **节点优先级没有"未来项"**——它只反映"已经拿到什么"，不反映"接下来还能拿到什么"；
2. **大量节点并列在 0**：be​am 保留 256 个节点时，**数百个 0 值节点在优先级上完全不可区分**，
   于是前沿实际是在"随机保留一批零值节点"，搜索只能靠**往下探**才发现价值（实测 chainDepth 到 18）；
3. **这解释了我此前所有的失败**：
   - 常数上界 `nodeValue + G`：因为祖先值是 0，要覆盖 71.5 的叶就必须 G≥71.5 → 等于不剪；G=20/25 则会误剪；
   - `beamPrunedOriginCount` 高达 14.8 万却仍低效：**它是在一堆无法区分的 0 值之间做取舍**；
   - 深度上限"能省则掉分"：因为深度是唯一在起作用的代理量，而它与价值不相关。

### 修复方向（与 owner 判断一致，且现在有量化依据）

**给节点优先级加"未来可达收益"项**，即
`priority'(node) = primaryValue(node) + futurePotential(node)`，其中 `futurePotential` 由**该节点状态**算出：
剩余轮次收入发放、当前路线未完成目标的得分、未领取的首拿/痕迹/科技/终局牌兑现等
（即我此前想做但没做的"逐节点结构上界"，只是现在**它同时是排序键，而不只是剪枝上界**）。

**验收指标已就绪**：修完后 `leafValue − min(祖先 nodeValue)` 的分布应**显著收紧**（基线：min 0 / p50 46 / max 71.5；
祖先值应不再是全部 0）。差距收紧 → B（上界剪枝）与 C'（贪心排序）同时变得可能。

## 十五、Round 52：**77% 的被展开节点优先级 ≤ 0，且没有任何节点 > 25**

482 单决策（干净基线 + 只读分桶计数器；动作/计划与基线一致 → 数据有效）：

| 优先级分桶（sortKey[2]） | 节点数 | 占比 |
|---|---|---|
| 未知 | 4 | 0.1% |
| **≤ 0** | **3153** | **77.0%** |
| (0, 10] | 534 | 13.0% |
| (10, 25] | 405 | 9.9% |
| (25, 50] | **0** | 0% |
| > 50 | **0** | 0% |

**全部 4096 个节点的优先级都 ≤ 25，其中 77% ≤ 0，没有任何节点超过 25。**

### 结论（这是整个性能问题的结构性病根）

1. **搜索在"零值平原"上做随机游走**：前沿只保留 256 个，而候选里有三千多个优先级 ≤0 的节点——
   beam 的取舍在**不可区分的并列**之间进行，等价于随机保留一批零值节点；
2. **价值只在深处出现**：所以搜索必须靠深探（chainDepth 到 18）才能碰到有价值的叶，节点预算因此被耗尽；
3. **一次解释全部现象**：
   - `beamPrunedOriginCount` 14.8 万却仍低效（在并列里做取舍）；
   - 常数上界 `nodeValue+G` 不可用（祖先值 0，叶值可达 71.5）；
   - 深度上限"能省则必掉分"（深度是这片平原上唯一在起作用的代理量）；
   - 打满 4096 共 43 次（平原太大，永远探不完）。

### 修复目标（可量化验收）

给优先级加**未来项**：`priority' = primaryValue + futurePotential(state)`，让平原产生**梯度**。

**验收指标**（改前基线已量出）：
- 482 展开节点中 `≤0` 的占比应从 **77%** 显著下降；
- `>25` 的节点应从 **0** 变为有实质数量（说明排序开始区分价值）；
- `leafValue − min(祖先节点值)` 的分布应从 p50 46 / max 71.5 **收紧**；
- 最终：打满 4096 次数下降、最慢决策下降，而**均分守住 113.5**。

## 十六、Round 54：**宽度去重不省节点**——两次实现都被实测否掉

### 测量（只读计数，482）

| 口径 | 值 |
|---|---|
| 展开节点 | 4096 |
| **其中"宽度重复"**（同 (根动作,目标,计划,proxyDepth,chainDepth,下一步动作) 已出现过） | **3392（83%）** |
| 不同宽度点 | **704** |

即：**83% 的节点预算花在"同一计划点+同一动作"的重复展开上**——正是 owner 指出的"几个动作类似的组合"。

### 实现一：前沿层去重（同宽度键只保留一个代表）

结果：`widthDuplicatedOriginCount = 2505`（丢掉 2505 个重复来源），但
**执行节点仍 4096、截断仍 true、剩余队列 253（比基线 244 还多）**；零值占比从 77% **恶化到 91%**。

原因：前沿是滚动窗口，被丢掉的重复项**本来也轮不到展开**（256 名额 vs 数千候选），
腾出的名额立刻被**同样零值的其他变体**填满。

### 实现二：展开层去重（同宽度键只展开第一次）

结果：`widthSkippedNodeCount = 657`，但**执行节点仍 4096、截断仍 true**，
且 `widthDistinctExpansionCount = 4096`——**搜索转而展开了另外 4096 个"此前没碰过的不同宽度点"**。

原因：零值平原上"计划点+动作"的组合近乎无限供给，砍掉重复只是让搜索**继续往别处探**，预算照样耗尽。

### 结论（收敛到 owner 最早的判断）

- **深度上限、前沿宽度去重、展开宽度去重——三种结构削减全部无法减少节点消耗**；
- 它们都是**症状**，真正的**闸门是"优先级没有梯度"**：搜索没有任何依据判断"这个点值不值得展开"，
  于是把预算均匀撒在整片平原上；
- **一旦有了未来价值梯度**，这三种机制（尤其展开层宽度去重 + beam 取舍）才会真正生效——
  因为届时"重复的宽度"与"无价值的宽度"才会被区分开。

**因此：`futurePotential`（设计见 `future-potential-design-20260913.md`）是唯一的前置项，其余优化都要排在它之后。**
