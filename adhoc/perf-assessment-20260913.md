## 剩余可行路线（二选一，需 owner 定）

1. **A 无损降每节点成本**：实测可动项合计约 25~30%（structuredClone 29.7%、GC 12.8%、契约序列化 ~6%、模块解析 1.9% 等）。
   天花：482 从 26.4s → **~22~24s**，**达不到 ≤5s**；但**零风险、零掉分**，可作为稳定性投入。
2. **新形态的上界（新建模）**：需要一个**沿路径单调不增**的量——正确的语义是
   "**该状态还能再兑现多少分**"（remaining realizable gain），而不是"当前持有多少潜力"。
   只有这种量才能同时满足：既作排序梯度、又作剪枝上界。**尚未实现**。

## 结论

- 三项硬指标中：**均分 113.5 守住**；截断 43 未归零；**最慢 25.5s 距 ≤5s 差约 5 倍**。
- 以现有机制，**≤5s 达不到**：所有"结构削减"要么掉分、要么不省节点；而 A 的天花板在 22s 以上。
- 唯一可能同时满足"守分 + ≤5s"的方向是第 2 条（新的单调上界），属新建模，工作量与不确定性都高。
- 现成可用的零截断配置仍是按需阶梯：**103 分 / 0 截断**（`budget-ladder-03`，opt-in）。

## 附：A 路线第一处具体开销（Round 62 定位）

`randomizer/game/ai/heuristic-decision-function.js` 的 `policyOutcomeView(outcomes)`（约 104-150 行）：

- 对**每个叶**调用一次递归 `canShare(leaf.observation)`——它会遍历冻结对象的**全部键**做合规校验；
- 之后对每个可共享叶再做一次 `JSON.stringify(leaf.observation)` 作为去重键。

单个决策的叶数可达 **~1500**（482 实测 `leafValueSampleCount=1515`），因此这里是
profile 中 `canShare` **4.0%**（外加 stringify 与 `copySerializable` 2.1%）的来源。

### 两个候选优化（按安全性排序）

1. **按对象身份跳过重复校验**：同一 `observation` 对象可能在多个叶间共享（该函数本身就要按 key 合并）。
   在**跨调用**层面加一个 `WeakSet<object>` 缓存"已验证可共享"的对象，命中即直接返回 true——
   纯加速，不改变判定结果。**风险低**，是首选。
2. **去重键改为对象身份**（`WeakMap<object, object>` 代替 `JSON.stringify` 字符串键）：
   省掉全部 stringify，但**去重粒度从"值相等"变为"同一对象"**，语义会变（不再合并值相等的不同对象）→
   **属行为变化**，需单独验收，不作为首选。

### 验收方式（A 路线门禁）

482/448/485 冷决策**逐字对比**（动作 actionId + 计划步数 + after 状态）+ 完整局逐动作差异 0 + 均分 113.5 不变；
计时用**同负载交替测量**（当前 loadavg ~4.5，适合做计时）。

## 附二：A 路线第二处目标——状态序列化/哈希（约 11%，且**可安全缓存**）

即**"序列化 + 哈希"一组约 11%**，而它们对**同一份不可变状态**是可缓存的。

### 实现（`randomizer/game/state/state-store.js:46` 的 `stableSerialize`）

- 调用点：`serialize(candidate = committedState)`（:461）与 `serializeForkSnapshot()`（:465）——同一份状态会被重复序列化；
- 状态由同文件的 `deepFreeze`（:39）冻结，**冻结对象不可变 → 序列化结果可安全缓存**；
- 方案：在该函数内加 `const serializedCache = new WeakMap();`，并**仅在 `Object.isFrozen(value)` 时**读写缓存
  （递归中的冻结子对象同样受益；非冻结的工作副本不走缓存，避免"可变对象被缓存后失效"的错误）；
- **行为等价性**：输出字符串逐字节不变（缓存只是跳过重复计算），因此可用现有门禁验收。

### 验收（按 Round 65 确立的方法）

1. 单测 99/99 + full-flow 1/1；
2. 482/448/485 冷决策**逐字对比**（动作 + 计划 + after）；
3. **profile 占比**：`stableSerialize` + `envelopeHash` + `stableHashSerialized` 合计应从 ~8.6% 明显下降
   （需多次采样取中位数，因单次 profile 有 ±0.5~1% 噪声）；
4. 完整局：逐动作差异 0、均分 113.5、整局耗时可测（预期整局 −5~10%）。

### 风险

- 若 `serialize(candidate)` 传入**未冻结**的候选（工作副本），缓存不生效（按设计），不会出错；
- 需确认 `deepFreeze` 覆盖全部进入序列化的状态对象（若某路径传入浅冻结对象而其后被就地修改，会读到陈旧缓存）——
  **这一点必须在实现时用 `Object.isFrozen` 之外的方式再核一遍**（例如确认 store 的所有提交路径都经 `deepFreeze`）。
